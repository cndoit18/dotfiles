# 可持续编码

在正确的抽象层解决当前问题：优先复用已有能力，修复根因，为有依据的变化建立稳定边界。

长期演进不等于预先设计未来，也不等于扩大改动范围。**没有真实变化点时，直接修改现有模块就是正确设计。**

每次改动遵循 **先让它工作（First Make it Work）→ 再让它正确（Then Make it Right）→ 遵循工程实践（Follow Practice）**。这不是先堆功能再统一补救：每一步都必须保持当前范围内的正确性、安全性和可验证性。

## 固定顺序

按以下顺序工作，不得跳过前两步直接写实现：

**复用调查 → 根因或职责定位 → 变化点判断 → 建立可观察验收 → 最小实现 → 立即验证**

“小步”以**一个可观察目标**为单位，而不是以修改行数为单位。对每个目标按 **建立验收 → 修改实现 → 立即验证** 完成闭环；缺陷修复还要先确认验收能发现当前缺陷，再修改实现，随后运行同一验收。不得等到全部实现完成后才统一验证。简单改动可以内部完成这些判断，但执行与未执行的状态必须来自真实工具结果。

## 1. 先建立执行契约

非平凡改动前，用不超过五行说明：

1. **目标**：可验证的输入、输出或症状。
2. **复用结论**：准备复用什么；不能复用时缺少什么能力。
3. **设计位置**：根因所属模块，或有依据的演进点。
4. **改动边界**：预计触碰的文件及明确不做的事。
5. **验证与停止**：验证命令、真实使用路径及完成条件。

若这些结论依赖猜测，先读取代码或提出一个关键问题，不要静默选择解释。实际验证已满足请求时，不为展示流程而重复修改或制造失败；报告证据并停止。

先厘清数据形状、核心不变量和领域术语，再写逻辑。以可检查的终态为目标；若中间态会暂时不完整，必须确认它在计划内且可回退。

## 2. 复用优先，但不强行复用

### 写代码前

1. 查看项目说明、依赖清单和相关模块，搜索领域名词、现有调用路径及相似能力。
2. 核对候选实现的接口语义、边界条件和失败行为，不能只按函数名判断可复用性。
3. 按以下顺序选择：
   - 项目中语义一致的现有模块或扩展点；
   - 语言、平台或框架的标准能力；
   - 项目已使用且适合当前语义的依赖；
   - 确认前三者不满足后，才写新实现。
4. 使用第三方能力前，核对本项目的实际版本和本地文档；不确定 API 时先验证。

### 禁止的造轮子

- 复制现有工具函数后只改少量细节，形成第二套实现。
- 为框架已经提供的机制再包一层没有新增语义的 wrapper。
- 新建与现有模块职责相同的 `utils`、`common`、`manager` 或 `helper`。
- 仅为避免少量简单代码而引入新依赖。

复用针对的是**同一知识和同一变化原因**，不是相似文本。语义不同、应独立变化的代码不得为了去重而耦合。

对不直观且会重复的机械工作，先手工完成一个代表性单元，再构建工具并核对其结果与手工样例一致；一次性、显而易见的工作不造工具。

## 3. 修根因，不在症状处打补丁

### 修复缺陷时

1. 先通过最小复现、日志或失败测试确认症状，观察真实退出状态和输出；不能只根据代码推断已复现。
2. 沿调用链定位被破坏的不变量，以及本应拥有该规则的模块。
3. 对可测试的缺陷，先写针对症状的回归测试，**实际运行并确认它因预期原因失败**，再修改实现。测试意外通过或错误不相关时，先修正测试或诊断，不能继续实现。
4. 在规则所有者处做最小修复，立即运行同一回归测试，确认它由失败变为通过。
5. 确实无法自动化或执行时，保留手动复现步骤，明确标记验证未执行，不得以静态阅读或命令存在代替运行结果。

若基于同一前提的两个修复都未通过同一验收，用一句话写出该前提，检查责任、信息或控制权是否分配错误；先纠正分配，再尝试下一个修复。

### 补丁信号与处理

| 补丁信号 | 应改成的设计动作 |
| --- | --- |
| 在调用方增加特殊条件 | 将规则收回负责该不变量的模块 |
| 增加布尔开关选择新旧逻辑 | 形成一条语义完整的规范路径；用户明确要求灰度时除外 |
| 捕获并吞掉异常以继续执行 | 修复错误来源，或在真正的系统边界明确处理 |
| 为绕过原实现再写一条平行路径 | 修复或替换原路径，避免两套行为漂移 |
| 每加一种情况就修改多个调用点 | 在真实变化点周围建立稳定接口 |
| 为无法修改的外部实现保留特殊逻辑 | 用 Adapter 隔离，不让外部细节泄漏到领域代码 |

不得把重试、兜底、空值或宽泛异常处理当作根因修复。用户明确要求紧急止血时可以先做临时方案，但必须说明限制，并将止血与根治区分开。

## 4. 只为真实变化点抽象

采用**更糟即更好（Worse is Better）**的取舍：在当前需求下，让实现简单性优先于假想完备性，先交付满足验收条件的可用版本，再依据真实使用演进。“更糟”仅指不为尚未出现的场景追求完整、一致和通用，不得牺牲当前正确性、安全性或验收标准。

应用**受保护变化（Protected Variations）**：识别可预见的变化或不稳定点，在其周围建立稳定接口，让调用方依赖稳定语义而不是可变实现。

同时用**近可分解性（Near Decomposability）**检验模块边界：让同一变化原因在模块内形成高内聚，模块之间只通过少量稳定契约协作，使多数真实任务能在少数边界内被独立理解、修改和测试。它减少的是人与 AI 必须同时加载的上下文，不是消灭依赖；跨模块事务、一致性、性能和端到端业务规则仍需整体分析与验证。

能删除多余状态、分支或重复决策时，先减法再加法。新需求暴露旧模型不再适合时，比较从零设计会如何建模，再拆成可验证的小步演进；不把从零设计等同于整体重写。

### 抽象需要的证据

至少存在一项当前证据：

- 当前同一变化点已有多个实现或明确支持的变体，或者多个调用方被迫了解同一可变细节；
- 同一设计决策已经散落在多处；
- 当前需求直接要求替换实现或扩展同类能力；
- 外部协议、供应商或不稳定依赖需要与领域逻辑隔离。

“以后可能会”“看起来更通用”“每段代码都应有接口”都不是证据。不要为假想需求预留配置、插件层、继承层级或通用框架。

### 建立边界时

1. 区分稳定语义与可变实现，把数据结构、算法和外部协议隐藏在边界之后。
2. 让常见调用保持简单，由模块内部吸收必要的复杂度，不把细节推给每个调用方。
3. 按调用需要明确输入、输出、副作用、错误和不变量；若正确调用仍必须阅读内部实现，先补齐接口语义或重新划分边界。
4. 接口只覆盖当前需要的能力，不添加没有消费者的参数和方法。
5. 非平凡设计至少比较两条路径：**直接修改现有模块**与**在变化点建立抽象**。选择整体理解和后续修改成本更低者。
6. 若无法为模块写出清晰的职责和接口说明，先重新划分，而不是继续实现。
7. 用当前真实变化做一次穿行检查：若同一实现细节迫使多个无关模块一起理解或修改，将该决策收回单一所有者。只是正常调用链时，不为减少跳转而抽象；内部出现独立变化轴时再递归划分，不制造巨型模块。

### 领域、数据与状态纪律

- 优先让数据结构和类型表达约束，使非法状态或值无法构造；不压制编译器或类型检查错误。
- 外部数据在入口解析、校验一次，内部依赖已验证的不变量；适合时将业务规则保持为纯函数。
- 需要重试或崩溃恢复的操作应有明确幂等语义：重复执行或从中断恢复后到达同一终态。
- 不需要共享可变状态的各方分别持有状态；必须共享时明确单一写者，并在结构或并发机制上落实。
- 领域术语跨模块或存在歧义时维护术语表；代码已经清晰且局部时，不额外建立文档或模型层。

## 5. 小步实现与即时验证

- 保持一条规范实现路径；除非用户明确要求迁移，不新增并行的 `v2`、`new` 或兼容分支。
- 优先扩展现有模块和测试，不做与当前需求无关的改名、清理或格式化。
- 每次只完成一个可验证目标，再进入下一个目标。一次验证失败时停在该目标，修复实现或验收后继续验证；不通过扩大改动范围绕过失败。
- 验证命令失败、超时或被环境阻断时，读取实际诊断；它不是测试通过，也不是产品行为已复现。不得重复绕过同一权限拒绝。若无法获得运行结果，停止声称完成验证，报告阻断与未验证范围。
- 注释解释非显然的约束和设计原因，不复述代码。
- 删除仅因本次改动而失效的代码和导入，不顺手删除既有死代码。
- 同一决策只保留一个权威位置，交付能解决当前问题的最小编辑。

### 测试与重构

- 对可测试的行为改动，先写一个会因预期原因失败的测试，再以最小实现使其通过；无法写出诚实测试时，不伪造形式测试，说明替代验证。
- 测试通过用户或调用方入口断言可见结果，不绑定私有实现；如果所有函数返回空值测试仍会通过，重写该测试。
- 重构先用行为测试或现有验收固定行为，再改变结构，最后证明行为未变。

## 6. 验证与收尾

1. 运行能证明当前结果的最窄测试，并观察其真实输出；把修复前失败与修复后通过关联到**同一个可观察断言**，而不是任意两次不同命令。
2. 缺陷修复确认回归测试在修复前失败、修复后通过；若无法执行，明确说明未验证的部分。
3. 对请求涉及的公开行为，从真实用户入口或实际调用路径走通输入到输出，不能只依赖编译或单元测试。若该行为就是现有单元测试覆盖的纯函数且没有额外集成风险，可说明为何该入口就是实际调用路径。
4. 审查最终 diff，逐项确认：
   - 没有新增未证明必要的重复实现；
   - 修复落在规则所有者处，而非症状周围；
   - 每个新抽象都有当前证据和明确消费者；
   - 同一知识只有一个权威所有者；
   - 下一次同类变化不需要修改多个无关模块；
   - 每行改动都服务于当前请求。
5. 验证通过且目标完成后停止，不继续扩展相邻重构。

### 按需质量工具

以下工具随 Skill 附带，路径相对本 `SKILL.md` 所在目录解析；从被检查项目的根目录运行。首次使用 Python 工具会联网安装上游依赖，必须遵守当前审批与项目约束；不要为小改动机械运行全套工具。

```bash
<skill-directory>/scripts/ub crapper [options]
<skill-directory>/scripts/ub dryer [options]
<skill-directory>/scripts/ub mutator [options]
<skill-directory>/scripts/ub uml
```

- **crapper**：检查本次触及的高风险函数；CRAP 达到 10 及以上时，通过拆分、补测试或两者降低复杂度与风险，不为指标重写清晰代码。
- **dryer**：检查 rank 0.8 及以上的结构性重复；先确认是否属于同一知识和变化原因，再决定是否去重。
- **mutator**：对本次修改的关键逻辑补充未覆盖行为并处理存活变异体；只删除已证明且属于本次范围的死代码。
- **uml**：需要理解复杂结构且现有工具不足时使用，不默认生成额外文档。

完整安装或迁移本 Skill 时，必须保留整个 `scripts/` 目录，不能只复制 `SKILL.md`。

### 工程实践

- 非平凡改动保留简要的决策与验证记录，交付时报告关键项，不逐条复述机械操作。最终分别列出“已执行并通过”“失败或阻断”“未执行”；禁止用计划运行的命令、测试文件存在或 Agent 自报作为通过证据。
- 大量搜索、阅读或独立分析可交给工具或子代理，主上下文保留结论与证据。
- 只有用户或项目指令明确要求时，才清理 worktree、提交或推送。未提交工作不得擅自删除；获授权提交时使用小步、有序的提交，并说明原因、改动和验证方式。

## 最终判断

交付前回答：

> 这次改动是否复用了正确的已有能力，消除了真正的规则缺口，并让下一次有依据的变化只需在少数明确边界内发生？

若答案是否定，先修正当前改动；若需要扩大用户已批准的范围，先说明原因并请求确认。
