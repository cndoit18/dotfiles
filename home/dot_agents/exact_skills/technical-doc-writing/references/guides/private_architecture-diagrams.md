# 架构图绘制与视觉验收

架构图不是把正文名词装进方框，而是用空间布局回答一个具体评审问题。默认交付**可编辑图源 + 已渲染图片**；只有 D2、Mermaid、LikeC4 或 SVG 源码而没有图片时，图示仍未完成。

## 1. 先固定这张图要回答的问题

画图前写一句内部读图任务，例如：“评审者能沿订单创建主链路，指出同步调用在哪里结束、异步分发从哪里开始。”随后只保留回答该问题所需的对象和关系。

- **系统边界与外部依赖**：用系统上下文图，不展开内部类、函数或文件。
- **可运行单元、存储与调用关系**：用容器／组件图；“容器”不等于 Docker。
- **请求顺序、分支与跨角色协作**：改用时序图或动态视图，不把架构图堆成流程图。
- **主机、网络区域与部署单元**：用部署图，不与逻辑组件混在同一层。
- 一张核心图优先保留约 5～9 个节点。更多对象先按读者任务拆成“总览 + 局部”，不要靠缩小字号塞进一页。

先列内部事实表：`节点（名称、职责、边界）`、`边（起点、终点、动作／协议、同步／异步）`。图中每个节点和每条边都应能回指事实表；未知项标 TBD，不为对称美观补关系。

## 2. 用布局表达架构，而不是只做装饰

查看 [版式样例](../../assets/architecture-style-example.png) 和它的 [SVG 源文件](../../assets/architecture-style-example.svg)。样例只用于校准阅读方向、间距、层级、连线和视觉克制，**不得把其中的系统、关系或结论复制到当前文档**。

按下列结构落图：

1. **主链路一条主轴**：调用链默认从左到右，分层架构默认从上到下。主链路节点放在同一行／列，分支放在上方或下方，避免“蛇形”阅读。
2. **网格对齐**：使用统一节点尺寸、行列间距和端口；同级节点等宽等高。先定网格再写 SVG，不逐节点随意试坐标。
3. **边界有语义**：系统边界用浅底、细线的大容器和明确标题；外部角色与第三方系统放在边界外。不要用多个彩色小框冒充分层。
4. **连线正交**：优先水平、垂直和直角折线，不用斜线。线不能穿过节点、节点标题、边界标题或其他边的标签；主链路尽量不交叉。
5. **箭头只表达一种方向**：一条边标一个动作或协议；双向交互拆成两条有标签的边，不使用含义不明的双箭头。
6. **同步与异步不只靠颜色**：同步用实线，消息发布／消费用虚线，并配短图例。只有确有第二种关系类型时才增加另一种线型。
7. **标签短而具体**：节点用“名称 + 必要职责／技术”，边用“调用”“写入”“发布 OrderCreated”等动词短语。长解释移到图后正文。

## 3. 使用可读、可维护的视觉规格

以最终插入文档后的尺寸验收，而不是只看编辑器里的放大视图。

- 白底或极浅灰底；标题 28～32 px，节点标题 18～22 px，辅助文字与边标签不小于 14 px。缩放至文档实际宽度后仍应清楚。
- 普通技术文档优先 1400～1800 px 宽的横向画布；PNG 用 2 倍像素导出，SVG 保留矢量版本。
- 一种主色表示应用服务，另一种低饱和色表示存储／消息；灰色表示外部对象。颜色通常不超过 3 类，线型与文字必须独立承载含义。
- 不使用渐变、立体效果、重阴影、装饰插画、无意义图标和彩虹式配色。不用 logo 代替组件名称。
- 节点内文字最多两行，保持内边距；边标签带白底或放在空白区，不能让线穿字。
- SVG 使用分组组织 `boundary`、`edges`、`nodes`，提供 `title` 与 `desc`；保留文本为文本，不将文字栅格化进图源。不同转换器对 `marker` 的支持不一致，节点图层也可能遮住箭头；若实际 PNG 中箭头缺失，改用显式三角形或调整图层／端点，不以 SVG 源码里有 `marker-end` 代替检查。

## 4. 选择现有渲染路径，不隐式安装工具

### D2：单页架构图默认路径

先用 D2 表达已核实的节点、容器和关系，不把布局试凑成技术事实。复制 [D2 样式类](../../assets/d2-architecture-style.d2) 中的 `service`、`store`、`external`、`direct`、`event` 定义，按实际语义添加模型；样式文件本身不包含任何当前系统。

先确认 `d2 version` 和 `d2 layout`。TALA 从 v0.9.0 起随 D2 内置；旧版本能力可能不同。CLI 不在 PATH 时，用 `D2_BIN` 指向已安装的二进制，不让脚本隐式安装。

```sh
bash <skill-root>/scripts/render_d2.sh --layout elk <output-dir>/architecture.d2 <output-dir>/architecture
D2_BIN=/path/to/d2 bash <skill-root>/scripts/render_d2.sh --layout tala <output-dir>/architecture.d2 <output-dir>/architecture-tala
```

脚本先 `d2 validate`，再生成同名 SVG 和 PNG，并输出结构化结果，默认使用 TALA。长调用链、依赖图或 TALA 重排不稳定时，再比较 ELK；若首版过宽、交叉、文字过小或分组失真，用**同一份 D2 源文件**渲染两种布局，再按实际图片选择，不改事实迎合布局，也不把某一种引擎当作所有图的固定最优解。

D2 模型除节点和边外，默认补齐评审语义：用 `shape: text` 和 `near: top-center` 添加标题，用 `near: top-right` 添加实线／虚线图例，用 `near: bottom-center` 添加读图结论；外部对象标签写明“外部角色／外部依赖”。异步分界优先写进对应边标签，例如“异步边界｜发布 OrderCreated”，不要添加悬浮且归属不明的装饰标签。图例或注释令布局恶化时，缩短文本或移到图旁正文，不牺牲主链路。

TALA 有随机性，小改动可能触发整体重排；需要复现时固定 `--tala-seeds`。先用 D2 内置字体渲染并检查中文，不要默认叠加多个大型 CJK 字体；自定义字体和放大导出可能触发 `retained font bytes exceed limit 67108864`，遇到时先回退内置字体，而不是反复重试。

### LikeC4：多视图或需要持续维护的架构

适合同一模型生成上下文、容器、组件、动态和部署视图。先确认目标环境已有 CLI 和版本；需要下载、安装或升级时先征得用户同意，不让 `npx`、`pnpm dlx` 隐式下载。

```sh
<existing-runner> likec4 validate --json --no-layout --file <model-file> <project-dir>
<existing-runner> likec4 export png -o <output-dir> <project-dir>
```

PNG 导出可能需要 Playwright；缺失时先说明，不自动安装。若用户接受可交互 HTML，可用 `likec4 build --output-single-file`，但它不能冒充已经交付的 PNG。

### Mermaid：小型调用链、流程和时序图

Mermaid 便于维护，但自动布局不一定满足架构图的阅读方向。生成后必须检查实际渲染图；出现主轴弯折、分组错位或标签碰撞时，简化视图或改用 D2／LikeC4／SVG，不继续堆不可维护的 `linkStyle` 补丁。

使用已存在且已获准的 CLI：

```sh
mmdc -i architecture.mmd -o architecture.svg -t neutral -b white
mmdc -i architecture.mmd -o architecture.png -t neutral -b white -s 2
```

`mmdc --version` 失败时先诊断；包装器中的 `npx -y @mermaid-js/mermaid-cli` 会下载依赖，不等于本地已安装。未获安装许可时改用可维护 SVG 或明确标“待渲染”。

### 可维护 SVG：单张静态图或自动布局不达标时

按第 2～3 节的网格生成 SVG，再用当前环境已有的浏览器或图像转换工具渲染 PNG。先确认工具支持 SVG，保存实际命令与退出码；不同平台不要假定 `sips`、浏览器或转换器一定存在。不要交付 base64 图片代替可编辑源文件。

## 5. 必须看实际图片，问题必须回修

源码解析成功不等于图可读。先生成最小完整版本并确认 PNG 已实际生成，再打开图片检查，避免只完成图源后中止。发现问题时，至少完成一次“修订 → 再渲染 → 复查”，不在未修复的情况下交付。

在最终显示尺寸逐项检查：

- [ ] 第一眼能找到起点、主链路和这张图要表达的结论。
- [ ] 所有已知节点、边、方向和协议与事实表一致，没有新增或漏画。
- [ ] 没有文字截断、节点重叠、线条穿字、箭头被遮挡、边界误包含或画布边缘裁切。
- [ ] 同步／异步、内部／外部、当前／规划状态可区分，且不只靠颜色。
- [ ] 标签在实际尺寸可读；没有用缩小字号解决拥挤。
- [ ] PNG 非空、尺寸正确，SVG／图源可编辑，Markdown 中引用的是实际存在的图片。

若上述任一项失败，优先删次要节点、拆图或调整网格，再重新渲染；不能只报告“代码已生成”。

随后把**实际图片（不提供图源）**和读图任务交给未参与绘图的独立读者代理，不提供事实表或标准答案，让它复述：起点、主链路、关键边界、同步／异步关系以及无法辨认之处。主 Agent 用原事实表核对复述，修复漏读和误读后再测。无法打开图片或无法安排独立代理时，明确写“未完成视觉检查”或“未完成图示读者代理测试”，不得声称图已验收。

## 6. 交付

- 默认交付 `architecture.png`（插入文档）、`architecture.svg`（矢量版本）和实际可编辑图源；D2 保留 `.d2`，LikeC4 项目可另含模型文件。
- Markdown 使用相对路径插入 PNG，图题直接说明图回答的问题；图源作为相邻链接，不用长段正文复述整张图。
- 渲染失败时仍保留可编辑模型，但显著标“图未渲染／未完成视觉检查”；不能把源码、占位符或自报成功当作成品图。
