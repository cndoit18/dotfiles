# 技术文档写作

把作者的知识网络转换成读者的阅读路径，再用明确的语篇关系实现这条路径。不要边想边写，也不要靠过渡词制造逻辑。

## 一、先确定读者任务

动笔前，在内部确定四项：

- **主要读者**：一个具体角色，不写“所有相关人员”。
- **阅读任务**：读完后要做出的决策、判断或操作。
- **共同基础**：读者已经知道的系统、术语和约束；只补他们缺少的背景。
- **阅读收益**：读者能从文档中带走什么，而不是作者想展示什么。

能从上下文确定的信息不要重复询问。关键信息缺失且会改变技术结论时，最多问两个针对性问题；其余未知项标为“假设”或“TBD”，不得编造。

写作和审校时逐段追问：

1. 它回答读者的哪个问题？
2. 读者为什么在这里需要它？
3. 删除它会妨碍哪个判断或操作？

三个问题都答不上来的内容，移到附录或删除。不要把推理过程、生成过程和资料罗列当正文。

## 二、先建语篇关系，再写段落

先把内容拆成短单元，每个单元只表达一个主张、证据、约束、示例或行动。再组织成层级大纲，并标明每个单元与上下文的主导关系。

使用下列受控 RST 关系，不自行创造近义标签：

| 关系 | 用途 | 检查点 |
| --- | --- | --- |
| 背景（Background） | 补足理解核心内容所需的上下文 | 只写读者尚不知道的背景 |
| 详述（Elaboration） | 为概括补充同一对象的细节 | 不趁机切换对象或层级 |
| 证据（Evidence） | 提高主张的可信度 | 观点、假设不能冒充证据 |
| 解决（Solutionhood） | 连接问题与解决方案 | 方案必须回应问题和约束 |
| 因果（Cause／Result） | 解释原因、机制或结果 | 时间先后不等于因果 |
| 条件（Condition） | 说明主张或方案成立的前提 | 条件应可判断、可验证 |
| 对比（Contrast） | 呈现对象间的关键差异 | 所有对象使用同一组比较维度 |
| 让步（Concession） | 承认限制，同时说明主张为何仍成立 | 不隐藏代价、风险和边界 |
| 顺序（Sequence） | 组织有依赖关系的步骤或事件 | 按时间或依赖排序，不伪造递进 |
| 并列（Joint） | 组织同层级、相互独立的单元 | 不把并列项写成因果或主从 |
| 总结（Summary） | 压缩已经表达的核心内容 | 不重复整章，不引入新主张 |

组织规则：

- 核心内容是**核（Nucleus）**，解释、证据和限制等支撑内容是**卫星（Satellite）**。并列步骤、选项等多核关系不要强行分出主次。
- 每个语篇跨度指定一种主导关系，内部可以嵌套其他关系；不要为了“一段一个标签”拆碎自然表达。
- 顺序由读者任务和语篇关系决定，不由“首先、其次、再次、最后”决定。
- 某单元无法接入关系结构时，选择澄清关系、调整位置、拆分或删除。禁止只补“因此”“然而”“同时”来掩盖断点。
- 暂时隐藏卫星内容，仍能辨认“问题—主张—方案—行动”的主线；恢复后，关键证据和限制必须完整。

关系图默认是内部工作稿，不把 RST 标签直接当成正式文档标题。

### 用渐进分化建立内容层级

渐进分化（Progressive Differentiation）要求先呈现最一般、包摄性最强的概念和整体框架，再逐步增加细节与特殊性。分层不是多设标题，而是按包摄关系控制信息出现的时机。

- 默认按“总括结论 → 关键组成 → 实现细节”展开；层级由概念包摄关系决定，不为凑层级多设标题。
- 子节只能细化父节的对象和主张，不得跨层加入实现细节，也不能无提示改变目标、范围或结论。
- 暂时隐藏下一层，上一层仍应完整自洽；展开下一层只增加精度和依据，不改变阅读主线。

### 用问题框架隔离目标与代码

问题框架（Problem Frames）区分待建系统（Machine）、现实问题领域（Problem Domains）和需求：需求描述现实世界中希望成立的条件，不是代码结构。

- **目标与问题**：只写现实角色、场景、领域约束、期望的可观察变化和验收标准；不得出现代码、类名、函数、表结构、接口签名或框架选型。
- **方案与机制**：用领域对象、责任、交互和因果关系说明解决思路，不以代码文件或类结构组织章节。
- **具体实现**：只有进入这一层才写代码、接口签名、依赖、框架和部署细节；每项选择必须回指一个目标或约束。

删除“具体实现”后，目标、理由和方案机制仍应完整；若删除代码就说不清目标，先补目标，不得用代码代替目标定义。

## 三、沿读者路径完成正文

- 先写决策所需的主线，再补证据、示例和实现细节；细节不得反复打断主线。
- 标题优先表达读者问题或本节结论，少用“相关说明”“其他事项”等容器标题。
- 每段只承担一个主要功能。背景、主张、证据和行动混在一段时，先拆分层级，再润色句子。
- 使用读者熟悉的稳定术语；首次出现且读者不熟悉的缩写或概念，就地解释。
- 多写明确的执行者、动作、对象、机制和边界，少写抽象名词堆叠。
- 技术事实、代码、接口和约束不得为追求流畅而改写。没有依据的数据不补造，未知处标“TBD”。
- 附录承载复现步骤、完整参数和补充证据，正文保留理解或决策所必需的部分。

### 用认知卸载决定何时配图

认知卸载（Cognitive Offloading）是用行动改变任务的信息加工需求，以降低内部认知需求。配图不是装饰，而是把读者需要在脑中重建的关系外化。

出现下列内容时，必须检查读者是否仍要靠文字重建关系；若是，生成对应图或表，而不是继续补字：

| 文字正在承担的工作 | 优先表达 |
| --- | --- |
| 多个组件、角色或系统之间的连接、调用和数据流向 | 架构图、拓扑图或数据流图 |
| 多步骤、分支、依赖或跨角色协作 | 流程图或时序图 |
| 状态及触发状态变化的条件 | 状态图 |
| 多个对象在同一组维度上的差异 | 对比表 |
| 真实数据的趋势、分布或比例 | 数据图表 |
| 界面位置、操作路径或运行结果 | 真实截图或带标注的界面图 |

图文配合规则：

- 图放在解释它的段落旁。图前一句说明读者要看什么，图后只补依据、限制或结论，不再逐句复述图。
- 图中对象、箭头、状态和界面名称必须与正文术语一致；没有含义的箭头、装饰性插画和只重复标题的图不保留。
- 图必须来自已知技术事实。未知关系标“TBD”，不得为画面完整编造组件、数据、流程或界面。
- 目标环境支持图片或画板时，实际生成并插入正文；只能交付图源时明确标“待渲染”，不得把源码、占位符或“此处应有图”当作已完成的图示。
- 没有需要外化的关系时不强行配图；图示不能替代必要的证据、假设和限制。

交付前，凡触发上述规则的内容必须已有实际图或表。无法渲染或插入时，明确列为未完成项，不得宣称图文文档已经完成。

### 用领会原则验证能否看懂

领会原则（Apprehension Principle）要求外部表征的结构与内容易被且准确地感知、理解。图已经生成不等于图有效；先保证看懂，再做适度美化，配色、阴影和圆角不能补救结构不清。

- 一张核心图只回答一个主要问题；出现多条主线时，拆图或分层，不靠增加更多说明文字补救。
- 起点、阅读方向、分组和箭头含义必须可辨；图例只保留必要编码，避免读者在图例与节点之间反复查找。
- 标签使用正文术语，关键关系直接标在连接线上；颜色不能作为区分关键信息的唯一手段。
- 删除不改变信息理解的装饰、重复节点和无含义连线，避免为了“好看”牺牲阅读顺序与关系准确性。

每张核心图还需由一名未参与绘图的目标读者，在不听作者讲解的情况下准确复述“对象是什么、关系是什么、结论是什么”；出现误读就改图，不用口头解释或额外长文补救。无法完成实测时标“未经读者验证”，不得声称通过领会检查。

## 四、分两轮审校

先改结构，再改句子；两轮不要混成同义词替换。

### 读者轮：能否被目标读者使用

- 用一个不了解写作过程的读者视角检查：能否找到建议、依据、代价和下一步？
- 删除读者不需要的科普、重复结论、空泛背景和写作过程叙述。
- 删除不承担信息或语篇功能的“本文将”“众所周知”“值得注意的是”“综上所述”等表达；连接词只有在关系真实存在时才保留。
- 合并语义重复的段落，拆掉为整齐而整齐的标题、列表和对仗句。
- 把“提升、优化、赋能、闭环”等空泛词替换为可观察的动作和结果；没有具体所指就删除。
- 不靠口语、口头禅或刻意“像人”来去 AI 味。每句提供新信息、每个抽象词有具体所指，才是目标。

### 关系轮：逻辑是否成立

- 能为主要章节画出关系树；不存在无法说明来意的孤立章节。
- 主张有证据，假设有标记，方案回应问题，风险对应具体机制。
- 因果、条件、对比、并列和顺序没有互相冒充；比较对象使用同一组维度。
- 每个段落与相邻内容的主导关系可说明，但不强求整篇只有一层或一种关系。
- 总结只收束已有内容，不重复铺陈，也不突然增加新结论。

## 五、技术方案的默认骨架

按读者任务增删，不机械补齐，不要求各节等长：

1. **建议与待决策**：先让读者知道要决定什么、当前建议是什么。
2. **问题与约束**：只写理解决策所需的背景、目标、非目标和约束。
3. **方案与机制**：说明核心结构、关键流程，以及它如何解决问题。
4. **依据与取舍**：给出证据、备选方案、比较维度、成本和风险。
5. **落地与验证**：写清依赖、步骤、验收、监控和回滚；未知负责人或日期不要虚构。
6. **附录**：放置主线不需要、但复核或复现需要的内容。

其他技术文档根据阅读任务重排此骨架，不把方案模板套到教程、排障记录或会议纪要上。

## 输出契约

- 用户要求成稿时，只交付文档及必要的文内 TBD，不展示读者分析、关系树、审校过程或本技能说明。
- 用户要求改写时，保留原有技术事实和决策；除非用户要求，不附长篇修改说明。
- 用户要求大纲时，输出读者可见的章节结构；关系标签可放在括号中辅助审阅，但不代替章节内容。
- 不声称经过真实读者测试，除非确实完成了该测试。

## 完成标准

交付前必须全部满足：

- 主要读者、阅读任务和核心建议在文档中可辨认。
- 每个主要章节都有读者用途和主导语篇关系，没有孤立内容。
- 主线不被背景、重复总结和实现细节淹没。
- 主张、证据、假设和未知项彼此区分。
- 没有仅靠连接词拼接的逻辑，没有为形式整齐制造的空内容。
- 初次阅读者无需理解作者的生成过程，即可说明“为什么做、做什么、凭什么、代价是什么、下一步是什么”。
