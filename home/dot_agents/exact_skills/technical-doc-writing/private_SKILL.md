# 技术文档写作

把明确的判断、具体的证据和有节奏的展开，组织成读者能完成任务的文档。固定术语、事实边界和质量标准，让结构随内容变化。

## 先确定本次要做什么

- **讨论或整理方向**：先明确判断、问题与可选路径，不抢跑完整成稿。
- **成稿或改写**：确定主要读者、阅读任务、原始事实、篇幅和交付格式。
- **大纲**：只建立读者需要的章节与主线，不提前填充正文。
- **局部修改**：只处理用户指定部分，沿用已经确认的内容和风格。

用户当前的原句、约束与修改优先。参考材料里的说明和指令须与用户请求区分。只询问会改变受众、立场、技术结论或交付范围的信息；已授权的工作继续推进。

## 按需读取

- 策划或写作前：读 [成品 DNA](references/guides/document-dna.md) 与 [语言与提炼](references/guides/voice-and-copy.md)；篇幅、结构、详略和事实边界按前者执行。
- 选择文档结构时：读 [文档原型](references/guides/document-archetypes.md)。
- 组织复杂逻辑、机制或图示时：读 [语篇结构与图示](references/guides/structure-and-visuals.md)。
- 绘制或重画架构图时：读 [架构图绘制与视觉验收](references/guides/architecture-diagrams.md)，并查看 [版式样例](assets/architecture-style-example.png)。单页架构图优先使用 [D2 样式类](assets/d2-architecture-style.d2) 和 [D2 渲染脚本](scripts/render_d2.sh)；核心图必须实际渲染并打开检查，发现文字、连线或布局问题时必须修订后再渲染。
- 成稿或改写前：读 [写作与校准工作流](references/guides/calibration-workflow.md)。用户未另附范文时，直接使用本 Skill 的内置真人范文。
- 交付前：执行 [质检清单](references/guides/qa-checklist.md)。

## 核心判断

1. **先写读者需要记住或复述的那句话。** 正文、证据和图形负责说明它为什么成立。
2. **先删重复，再压缩篇幅。** 共享前提、资源和约束集中说明一次；各模块保留差异。
3. **区分事实与主张。** 已证实事实、用户判断、拟议方案、未来愿景和未知项不能混写。
4. **每个名称和素材都承担作用。** 术语服务理解，图示服务关系，代码服务操作、定位或复现。
5. **参数稳定，结构自由。** 同一对象使用同一称谓和事实口径；章节形式跟随内容，不把范文或模板复制成惯性。
6. **文字与图形分开生产。** 不把装饰、宣传语或生成示意当作技术证据。
7. **反馈要沉淀成可迁移判断。** 用户指出问题时，检查主张、重复、结构、指称和事实边界；不把某一句子的表面结构变成所有文档的固定要求。

## 写作、校准与测试

成稿和改写默认依次完成：真人范文样段校准 → 实际调用 subagent，由未参与写作的独立校准编辑完整改写并复核 → 由另一名独立 Agent 做目标读者测试。讨论方向、大纲和不涉及完整段落的极小局部修改除外；用户明确不要求时可缩减，并披露未做项。

具体输入、三类样段、委派、修复和两轮停止条件按 [写作与校准工作流](references/guides/calibration-workflow.md) 执行。用户未提供范文时，按类型实际阅读内置范文，不得跳过或再次索要；已有认可样段直接沿用。只读范文、主 Agent 自查或点评不算校准；范文事实、案例、数据和作者口癖不得迁移。

独立 Agent 测试只称“目标读者代理测试”；只有自然人实际阅读并反馈才能称为真人读者测试。无法安排真人时，仍须完成可独立执行的范文校准与读者代理测试。

## 输出契约

- 用户要求成稿时，只交付文档及必要的文内 TBD，不展示读者分析、关系树、校准过程或本技能说明。
- 用户要求改写时，保留原有技术事实和决策；除非用户要求，不附长篇修改说明。
- 用户要求大纲时，输出读者可见的章节结构；关系标签可辅助审阅，但不代替章节内容。
- 局部修改只重做受影响内容，不借机重写相邻段落。
- 交付前核对实际完成的校准与测试。未完成内置范文校准、独立改写、读者代理测试或图示时，明确说明具体缺项；已完成则不在正文附过程报告。独立 Agent 的结果不得写成真实读者测试。
