# 技术文档写作

把作者的知识网络转换成具体读者完成任务的阅读路径。先确定读者与语篇结构，再写正文；不要为了展示理论、实现细节或写作过程增加阅读负担。

## 篇幅契约（优先执行）

默认交付 5 分钟内可读完的决策稿，而非完整知识库。用户明确指定篇幅或要求详细版、完整手册、审计材料时，以用户要求为准。

- 未指定篇幅时，中文正文不超过 2000 字、最多 4 个一级章节；开头用不超过 150 字给出结论、关键理由和待决策项。短任务按需要更短，不为接近上限补字。
- 每节最多 3 个要点。**能用图清晰表达的内容优先配图**，不能用长段文字或短列表替代；适合同维度比较的内容用一张表。同一信息不在图、表、列表和正文中重复表达。
- 每段都必须通过删除测试：删掉它会妨碍读者的哪个判断或操作？没有答案就删。资料数量、作者掌握的信息和模板完整度都不是扩写理由。
- 详细推演、落选方案、完整参数、复现步骤和补充证据默认不生成，也不附在正文后。用户需要详稿时，先交付短正文，列出可另行补充的材料，不自动展开。
- 不得为凑上限删除关键风险、约束、证据或未知项；确实装不下时，保留决策必需内容并说明未展开项，不得静默超限。
- 交付前实际检查字数和结构；超限就合并重复、删除低价值背景与实现细节，不得把删掉的文字原样搬进附录。字数约束与章节、要点限量必须同时满足。

## 一、先确定读者任务

动笔前，在内部确定：

- **主要读者**：一个具体角色，不写“所有相关人员”。
- **阅读任务**：读完后要做出的决策、判断或操作。
- **共同基础**：读者已经知道的系统、术语和约束；只补他们缺少的背景。
- **阅读收益**：读者能带走什么，而不是作者想展示什么。
- **交付类型**：成稿、改写或大纲，以及用户指定的格式和范围。

能从上下文确定的信息不要重复询问。关键信息缺失且会改变技术结论时，最多问两个针对性问题；其余未知项标为“假设”或“TBD”，不得编造。

### 用受话人设计选择内容

受话人设计（Recipient Design）指表达者根据特定接收者的知识、关系和共同经历组织措辞、指称与详略。用它决定写什么、写给谁，而不是在正文展示这个理论。

- 逐段确认：它回答读者的哪个问题？读者为什么在这里需要它？删除它会妨碍哪个判断或操作？三个问题都答不上来的内容，移到附录或删除。
- 不重复读者已掌握的背景；读者缺少且理解主线必需的背景，就地补足。
- 实现名称必须经阅读任务准入：读者需要操作、定位或复现时保留，否则用“谁对什么做什么、得到什么”表达，或移至附录。
- 代码名、字段名、框架名和缩写不能先于其作用出现。确需保留时，先用读者语言说明用途，再给出名称。
- 推理过程、生成过程和资料罗列不进入正文；复核或复现所需的材料放入附录。

### 用沟通适应理论校准表达

沟通适应理论（Communication Accommodation Theory）研究人们如何根据交际对象与关系调整语言。技术写作采用趋同：向读者的词汇、句长和认知习惯靠拢，同时保留技术精度，不居高临下地过度简化。

- 使用读者熟悉的稳定术语；首次出现且读者不熟悉的概念，就地解释，不用另一个陌生术语解释它。
- 多写明确的执行者、动作、对象、机制和结果，少用抽象名词堆叠。术语本身不能充当解释。
- 优先正向写出实际含义。不要用连续的“不代表”“不等于”“并非”“不是”代替正文；只有防止某种具体误读且该误读会影响判断时，才保留必要的否定边界，并同时写出实际含义。
- 不为迁就读者而修改技术事实、代码、接口、约束或风险；没有依据的数据不补造。
- 上述理论只用于内部写作与审校。除非文档主题就是该理论或读者需要出处，否则成稿不展示理论名、英文缩写和写作规则自述。

## 二、先建语篇关系，再写段落

先把内容拆成短单元，每个单元只表达一个主张、证据、约束、示例或行动，再组织成层级大纲，并标明各单元与上下文的主导关系。

使用下列受控 RST 关系，不自行创造近义标签：

| 关系 | 用途 | 检查点 |
| --- | --- | --- |
| 背景（Background） | 补足理解核心内容所需的上下文 | 只写读者尚不知道的背景 |
| 详述（Elaboration） | 为概括补充同一对象的细节 | 不切换对象或层级 |
| 证据（Evidence） | 提高主张的可信度 | 观点、假设不能冒充证据 |
| 解决（Solutionhood） | 连接问题与解决方案 | 方案必须回应问题和约束 |
| 因果（Cause／Result） | 解释原因、机制或结果 | 时间先后不等于因果 |
| 条件（Condition） | 说明主张或方案成立的前提 | 条件应可判断、可验证 |
| 对比（Contrast） | 呈现对象间的关键差异 | 所有对象使用同一组比较维度 |
| 让步（Concession） | 承认限制，同时说明主张为何仍成立 | 不隐藏代价、风险和边界 |
| 顺序（Sequence） | 组织有依赖关系的步骤或事件 | 按时间或依赖排序 |
| 并列（Joint） | 组织同层级、相互独立的单元 | 不把并列项写成因果或主从 |
| 总结（Summary） | 压缩已经表达的核心内容 | 不重复整章，不引入新主张 |

组织规则：

- 核心内容是**核（Nucleus）**，解释、证据和限制等支撑内容是**卫星（Satellite）**；并列步骤、选项等多核关系不要强行分出主次。
- 每个语篇跨度指定一种主导关系，内部可以嵌套其他关系；不要为了“一段一个标签”拆碎自然表达。
- 顺序由读者任务和语篇关系决定，不由“首先、其次、再次、最后”决定。
- 无法接入关系结构的内容，应澄清关系、调整位置、拆分或删除；禁止只补连接词掩盖断点。
- 暂时隐藏卫星内容，仍能辨认“问题—主张—方案—行动”的主线；恢复后，关键证据和限制必须完整。
- 关系图默认是内部工作稿，不把 RST 标签直接当成正式文档标题。

### 用渐进分化建立内容层级

渐进分化（Progressive Differentiation）要求先呈现最一般、包摄性最强的概念和整体框架，再逐步增加细节与特殊性。

- 默认按“总括结论 → 关键组成 → 实现细节”展开；层级由概念包摄关系决定，不为凑层级多设标题。
- 子节只能细化父节的对象和主张，不得跨层加入实现细节，也不能无提示改变目标、范围或结论。
- 隐藏下一层时，上一层仍应完整自洽；展开下一层只增加精度和依据，不改变阅读主线。

### 用问题框架隔离目标与代码

问题框架（Problem Frames）区分待建系统、现实问题领域和需求。需求描述现实世界中希望成立的条件，不是代码结构。

- **目标与问题**：只写现实角色、场景、领域约束、期望的可观察变化和验收标准，不出现代码、类名、函数、表结构、接口签名或框架选型。
- **方案与机制**：用领域对象、责任、交互和因果关系说明解决思路，不以代码文件或类结构组织章节。
- **具体实现**：只有进入这一层才写代码、接口签名、依赖、框架和部署细节；每项选择必须回指一个目标或约束。

删除“具体实现”后，目标、理由和方案机制仍应完整；若删除代码就说不清目标，先补目标，不得用代码代替目标定义。

## 三、沿读者路径完成正文

- 先写决策所需的主线；只补会改变结论的证据、示例和实现细节，其他内容按篇幅契约删除或不展开。
- 标题优先表达读者问题或本节结论，少用“相关说明”“其他事项”等容器标题。
- 每段只承担一个主要功能；背景、主张、证据和行动混在一段时，先拆分层级，再润色句子。
- 附录仅在用户要求或复核、复现必需时提供，并遵循篇幅契约；正文只保留理解或决策所必需的部分。

### 图示优先：先判断能否配图

认知卸载（Cognitive Offloading）是通过外部表征降低内部认知需求。写作时先检查内容能否用图或表准确表达；**能配图讲清楚的，默认实际配图**，再用少量文字补充结论、依据和限制，不以长段文字代替图示。出现下列内容时，优先生成对应图或表，而不是继续补字：

| 文字正在承担的工作 | 优先表达 |
| --- | --- |
| 多个组件、角色或系统之间的连接、调用和数据流向 | 架构图、拓扑图或数据流图 |
| 多步骤、分支、依赖或跨角色协作 | 流程图或时序图 |
| 状态及触发状态变化的条件 | 状态图 |
| 多个对象在同一组维度上的差异 | 对比表 |
| 真实数据的趋势、分布或比例 | 数据图表 |
| 界面位置、操作路径或运行结果 | 真实截图或带标注的界面图 |

图文配合规则：

- 图放在其回答的问题旁。图前最多一句说明读图重点，图后只补图无法表达的依据、限制或结论，不逐句复述图，也不再写一段与图等价的流程或关系描述。
- 图中对象、箭头、状态和界面名称必须与正文术语一致；删除装饰性插画、无含义箭头和重复节点。
- 图必须来自已知技术事实；未知关系标“TBD”，不得为画面完整编造组件、数据、流程或界面。
- 目标环境支持图片或画板时，实际生成并插入正文；只能交付图源时明确标“待渲染”，不得把源码或占位符当作已完成的图示。
- 不适合图示的纯结论、证据或限制不强行配图；装饰性配图不算完成。图示不能替代必要的证据、假设和限制。
- 交付前，凡能用图清晰表达的内容必须已有实际图；表格不能替代本应使用的图。无法渲染或插入时，明确列为未完成项。

### 用领会原则验证能否看懂

领会原则（Apprehension Principle）要求外部表征的结构与内容易被且准确地感知、理解。先保证看懂，再做适度美化。

- 一张核心图只回答一个主要问题；出现多条主线时，拆图或分层。
- 起点、阅读方向、分组和箭头含义必须可辨；图例只保留必要编码。
- 标签使用正文术语，关键关系直接标在连接线上；颜色不能作为区分关键信息的唯一手段。
- 删除不改变信息理解的装饰、重复节点和无含义连线，不以配色、阴影和圆角补救结构不清。
- 每张核心图应由一名未参与绘图的目标读者，在不听作者讲解的情况下复述“对象是什么、关系是什么、结论是什么”；出现误读就改图。无法实测时标“未经读者验证”，不得声称通过领会检查。

## 四、按阅读任务组织文档

技术方案默认只写以下四部分，按需合并，不机械补齐：

1. **建议与问题**：当前建议、待决策项，以及理解决策必需的目标和约束。
2. **方案与机制**：核心结构、关键流程，以及它如何解决问题。
3. **依据与代价**：会改变决策的证据、取舍、成本和风险。
4. **落地与验证**：关键依赖、灰度、验收、监控和回滚；未知负责人或日期不要虚构。

其他技术文档根据阅读任务重排，不把方案模板套到教程、排障记录或会议纪要上。详细推演、完整参数、复现步骤和补充证据默认不展开，遵循篇幅契约。

## 五、分两轮审校、独立评审并交付

先由主 Agent 改结构，再改句子，最后由独立 Agent 评审；不把前两轮混成同义词替换。

### 读者轮：能否被目标读者使用

- 能否找到建议、依据、代价和下一步？删除读者不需要的科普、重复结论、空泛背景和写作过程叙述。
- 删除不承担信息或语篇功能的“本文将”“众所周知”“值得注意的是”“综上所述”等表达；连接词只有在关系真实存在时才保留。
- 合并语义重复的段落，拆掉为整齐而整齐的标题、列表和对仗句。
- 把“提升、优化、赋能、闭环”等空泛词替换为可观察的动作和结果；没有具体所指就删除。
- 不靠口语、口头禅或刻意“像人”来去 AI 味。每句提供新信息，每个抽象词有具体所指。

### 关系轮：逻辑是否成立

- 主要章节能接入关系树；主张有证据，假设有标记，方案回应问题，风险对应具体机制。
- 因果、条件、对比、并列和顺序没有互相冒充；比较对象使用同一组维度。
- 每个段落与相邻内容的主导关系可说明，但不强求整篇只有一层或一种关系。
- 总结只收束已有内容，不重复铺陈，也不突然增加新结论。

### 独立 Agent 评审轮：是否经得住复核

- 成稿、改写或大纲完成后、交付前，必须使用 `subagent` 启动一名未参与写作的独立评审 Agent；不得用主 Agent 自查或复述上述两轮审校代替。
- 向评审 Agent 提供主要读者、阅读任务、交付类型、待评审稿和完成标准；同时提供用户原始需求、原文（改写任务）及写作依据的原始资料，不得只提供主 Agent 整理的意图摘要。要求它先独立通读原文和原始需求，再阅读待评审稿，只评审、不改稿，按“原始意图一致性、篇幅与信息必要性、图示优先与图文配合、读者可用性、语篇关系、事实与边界”列出问题，优先给出删除项，不建议新增非必要内容，并标明位置、影响和修改建议。
- 评审 Agent 必须单独给出原始意图一致性结论，明确判定“一致／部分一致／不一致”，逐项核对核心目标、范围、关键事实、决策、约束和非目标，指出遗漏、偏移、误读或擅自新增。没有原文时，以用户原始需求和原始资料为对照；依据不足时判为“无法确认”，不得由主 Agent 代做或凭空推断，未给出该结论不得交付。
- 主 Agent 逐条处理评审意见：修复成立的问题；不采纳时记录具体理由。修改影响主线、关键结论或图表时，交由同一评审 Agent 复核后再交付。
- 评审意见和修订记录默认不进入成稿。独立 Agent 评审不等于真实读者测试，不得据此声称文档已通过读者验证。
- 子 Agent 不可用或调用失败时，明确告知用户“未完成独立 Agent 评审”，不得将主 Agent 自查描述为独立评审。

## 输出契约

- 用户要求成稿时，只交付文档及必要的文内 TBD，不展示读者分析、关系树、审校过程或本技能说明。
- 用户要求改写时，保留原有技术事实和决策；除非用户要求，不附长篇修改说明。
- 用户要求大纲时，输出读者可见的章节结构；关系标签可放在括号中辅助审阅，但不代替章节内容。
- 不声称经过真实读者测试，除非确实完成了该测试。

## 完成标准

交付前逐项检查：

- 用户未指定篇幅时，正文不超过 2000 字、最多 4 个一级章节且开头摘要不超过 150 字；未通过附录转移字数。

- 主要读者、阅读任务和核心建议可辨认；每个主要章节都有读者用途和主导语篇关系。
- 每个保留的实现名称都服务于操作、定位或复现；其他名称已删除或移至附录。
- 读者不熟悉的首次出现术语均已就地解释，且解释不依赖另一个陌生术语。
- 不存在用连续否定句代替实际说明；保留的否定边界对应具体误读，并给出实际含义。
- 隐藏实现细节后，目标、理由和方案机制仍完整；隐藏卫星内容后，主线仍清楚。
- 主张、证据、假设和未知项彼此区分，没有仅靠连接词拼接的逻辑。
- 能用图清晰表达的架构、流程、状态、关系和界面均已实际配图，图后没有重复文字；仅交付源码、占位符或用表格替代本应使用的图，均已标为未完成；未经读者验证的图已明确标注。
- 独立评审 Agent 已返回评审结果，主 Agent 已逐条处理；需要复核的修改已由同一评审 Agent 复核。
- 初次阅读者无需理解作者的生成过程，即可说明“为什么做、做什么、凭什么、代价是什么、下一步是什么”。
