# Skill 编写与信息架构

只在创建新 Skill 或需要重构信息架构时读取本文件。

## 1. 先证明值得做成 Skill

适合沉淀：

- 重复发生且需要领域知识、项目约定或特殊工具的任务；
- 容易漏步、需要可复现流程或审计证据的任务；
- 无 Skill 基线已经暴露出稳定失败模式的任务。

一次性任务、模型已经稳定完成的简单操作，不必做成 Skill。若一个 Skill 包含多个无关交付物，先拆分能力边界。

## 2. 写触发描述

`description` 是路由接口，至少包含：

1. 做什么：用用户能表达的意图描述能力；
2. 何时用：覆盖直接名称和不说专业术语的隐性场景；
3. 何时不用：只写能区分相邻能力的实质边界。

不要把内部步骤、文件清单、理论背景和测试句原文堆进 description。正例不触发时补充通用意图类别；负例误触发时收紧职责和排除范围。不要通过不断加入失败 query 的关键词过拟合。

## 3. 写执行正文

推荐顺序：

```text
能力目标
→ 必要输入与缺失输入处理
→ 执行流程
→ 输出与验收
→ 禁止事项和停止条件
→ 按需资源索引
```

简单 Skill 可以合并标题。每段都应能回答“删除后会影响哪个可观察结果”；不能回答的删除或合并。

优先保留非显然知识：API 怪癖、项目命名、软删除、字段语义、容易遗漏的验证。不要复述通用编程常识，不索取隐藏思维链；需要可核验性时要求简洁依据和检查结果。

## 4. 匹配自由度

- **高自由度**：多种方法都合理、依赖上下文判断的分析任务。给目标、原则和验收。
- **中自由度**：存在推荐模式但允许变化。给参数化流程、模板或短示例。
- **低自由度**：顺序严格、格式脆弱或操作高风险。给确定脚本、验证器和人工确认点。

解释规则存在的原因，避免无差别强化命令。高风险操作必须明确范围、禁止动作、不可逆操作确认点和完成后的停止条件。

## 5. 组织资源

```text
skill-name/
├── SKILL.md
├── references/   # 特定分支才需要的知识
├── scripts/      # 重复、脆弱或确定性的操作
├── assets/       # 模板和静态资源
└── evals/        # 触发与任务评测
```

- SKILL.md 保持主流程可读；接近 500 行或 5000 tokens 前主动拆分。
- 所有 references 从 SKILL.md 直接链接，避免引用套引用。
- 较长参考文件在顶部提供目录，文件职责保持单一。
- 脚本非交互运行，提供 `--help`，标准输出给结构化结果，标准错误给诊断。
- 脚本路径相对 Skill 根目录解析，不假设调用者当前目录。
- 不为了假想通用性引入依赖、插件层或配置框架。

## 6. 建立有效验收

每条验收必须可观察，并追溯到根本任务或明确约束。避免：

- 只检查标题、格式和字数，不检查任务是否完成；
- 使用“专业”“合理”“较好”等不可判定词；
- 强制无关措辞，使正确答案假失败；
- 让参与创作的 Agent 自评后直接宣布通过。

创建或优化生成型 Skill 时，必须把产物再次交给独立 Agent 做二阶评测。
