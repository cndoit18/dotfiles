# Skill 故障诊断

优化前使用。先收集失败证据，再选择修改层；不要默认增加更多命令。

## 1. 故障分类

| 层 | 观察信号 | 首要修改 | 不应先做什么 |
|---|---|---|---|
| 路由 | 正例不加载、近似负例加载、相邻 Skill 竞争 | name、description、能力边界 | 重写执行正文 |
| 执行 | 已加载但漏步、误解输入、输出偏离、过度提问 | 目标、前置条件、流程、契约 | 继续扩大 description |
| 资源 | 找不到文件、重复写脚本、读取无关资料、上下文膨胀 | 资源索引、路径、脚本、引用层级 | 增加更多背景资料 |
| 验收 | 无 Skill 也通过、两版都失败、Judge 偏袒、自报成功 | 用例、断言、基线、评审独立性 | 根据无效分数改 Skill |

## 2. 最小复现

每个失败至少记录：

- 原始用户输入，不改写成更明确的版本；
- 目标运行时、模型和可用 Skill 目录；
- 实际加载事件、关键工具调用和输出；
- 预期结果与实际结果的可观察差异；
- 是否稳定复现，以及运行次数。

缺少加载日志时，只能确认输出异常，不能断言是路由故障。缺少执行轨迹时，不猜测 Agent 为什么忽略指令。

## 3. 根因选择

按顺序检查：

1. **目标错误**：Skill 的能力边界本身不符合用户意图，先修目标。
2. **契约缺失**：目标正确但输入、交付、边界或验收不清，补最小契约。
3. **信息位置错误**：关键规则埋在按需资源中，或 description 承担执行细节，调整位置。
4. **确定性工作遗漏**：每次运行都重复编写相同解析、验证或转换代码，沉淀脚本。
5. **过度约束**：规则互相冲突、步骤膨胀、Agent 浪费工作，删除无效规则并做回归。

## 4. 优化纪律

- 优化前保存基线快照，不能直接覆盖唯一旧版本。
- 一轮尽量只改变一个故障层，保留可解释的归因。
- 用训练集失败指导修改，用固定验证集检查泛化。
- 对既有能力增加回归用例，不只验证新修复的症状。
- 若新旧两版同样失败，先检查运行时、工具、用例和断言，不继续堆提示词。
- 若无 Skill 与有 Skill 同样通过，删除无区分度断言，并重新判断 Skill 是否值得存在。
