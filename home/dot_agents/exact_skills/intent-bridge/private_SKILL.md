# Intent Bridge

把模糊需求转成用户能判断、Agent 能执行、结果能验收的执行规格。目标是**最小充分澄清**，不是问遍整棵决策树。

不能承诺需求或规格“没有偏差”。必须让偏差可追踪、可发现、可纠正，并用真实结果校验 Agent 是否理解了意图。

## 核心规则

- **先查证，后提问**：能从代码库、文档、现有资产或工具结果中获得的答案，不向用户提问。
- **只问人类才能回答的事**：目标、优先级、偏好和风险接受度可以问；技术事实和可验证问题自行解决。
- **区分事实与猜测**：每条决定记录来源，并标为“用户确认”“证据核实”“AI推断”或“可逆默认”。推断和默认不得静默升级为确认。
- **为决策而问，不为完备而问**：答案不会改变任何行动的，不问。
- **让用户判断具体结果**：不要求用户掌握设计、工程或 AI 术语。
- **持续维护同一份规格**：每轮更新，不把原始聊天记录当作最终事实源。

## 工作流程

### 一、建立最小初始规格

从当前上下文提取已知信息，不重复询问：

- 根本需求：“在【场景】中，为【对象】实现【可观察结果】”。
- 唯一交付物、目标 Agent、运行环境和已有输入。
- 硬约束、非目标、权限边界和不可逆操作。
- 用户已经表达的偏好、参考例子及反例。

缺失信息先标为假设，不编造。根本需求存在多个互斥解释，且选择会显著改变结果时，才进入提问。

### 二、先消除无需交互的不确定性

把未知项分为三类：

1. **可自行核实**：立即查代码、文档、资产或运行结果。
2. **可采用默认**：影响小且容易撤销的，采用推荐默认并记录。
3. **必须由用户决定**：会影响目标、关键偏好、高成本返工或不可逆结果的，形成候选问题。

若最终接收规格的是另一个 Agent，记录其名称与能力边界；不知道时不要声称已适配特定工具。

### 三、用信息价值选择最小下一问

对每个候选问题在内部检查：

- 不同答案分别会改变哪个决定？
- 哪个答案会剪掉最多后续分支或解除关键依赖？
- 不提问的返工风险是否高于这一次交互成本？

所有答案都导致同一行动的，删除该问题。低价值问题改用可逆默认，不追求消除全部不确定性。

每轮只处理一个决策主题。最多合并三个**同层、互不依赖**的判断；后续问题依赖本轮答案时，不得提前堆问。每个问题附推荐答案及一句理由。

### 四、把问题降到用户的经验层

沿抽象阶梯向下：先说明用户能看到或感受到的影响，再给具体例子。不要只解释术语定义。

普通问题使用以下格式；视觉问题优先附参考图、截图或可交互原型：

```text
这会影响：<用户能观察到的结果>
<一个具体问题>
A. <具体结果及代价>
B. <具体结果及代价>
推荐：<A 或 B>，因为<一句日常语言理由>
可回答：A / B / 都不像 / 看不懂 / 无法判断 / 你决定
```

没有可视化工具时，用具体场景描述可观察结果，不得声称展示了实际页面。

用户回复“看不懂”时：

1. 不换一组术语重述，只下降到“用户会看到什么、每个选择会失去什么”。
2. 同一问题最多具体化重问一次。
3. 仍无法判断且决定可逆时，采用推荐默认，记录后继续。
4. 决定不可逆或影响重大时，不静默默认；暂停该分支，只澄清可理解的后果选择。

### 五、用比较代替抽象描述

用户无法描述视觉或体验偏好时，不要求“说得再详细一点”，改用**方格技术**：

1. 围绕当前高价值未知项，选取或低成本生成三个有明显差异的候选。
2. 让用户回答：“哪两个相似？第三个在哪一点不同？”允许直接指向页面或只选“更像／更不像”。
3. 把差异整理成候选维度，例如“疏—密”“安静—张扬”，先标为“AI推断”。
4. 若推断仍会影响关键实现，再用下一组具体候选检验；一旦足以决定下一版，不再为完善理论而增加比较轮次。

仅当优先级仍不清楚且会改变实现时，使用**阶梯访谈法**，最多连续追问两次：

- “这个不同会带来什么结果？”
- “这个结果为什么重要？”

把答案记为“属性 → 结果 → 价值 → 优先级”。得到可指导取舍的优先级即停止，不机械追问“为什么”。

### 六、满足停止条件即结束提问

同时满足以下条件后，不再采访：

- 剩余问题的答案都不会实质改变下一步实现，或不值得其交互成本。
- 没有未处理的重大冲突、高风险或不可逆未知项。
- 低影响未知项已有明确、可撤销的默认。
- 已能定义最小端到端交付物及其目标层验收。

停止不代表“所有细节都已确定”，也不代表“AI 已证明完全理解”。

### 七、生成可执行规格

最终规格使用以下结构；无内容的非必要小节可省略，不得编造占位信息：

```markdown
# 执行规格 v<N>

## 目标 Agent 与唯一交付物
<接收者、环境、交付物>

## 根本目标与成功结果
<场景、对象、可观察变化；说明为何值得做>

## 非目标与不变式
<明确不做什么；全程不得破坏的边界>

## 输入、前置条件与权限
<已有输入、操作范围、需要人工确认的不可逆动作>

## 决策与偏好
| ID | 内容 | 来源 | 状态 | 优先级 | 可逆性 |
|---|---|---|---|---|---|
| D1 | <决定> | <用户选择、参考资产或核实证据> | <用户确认/证据核实/AI推断/可逆默认> | <P0/P1/P2> | <是/否> |

## 执行步骤
1. <按依赖排序的最小端到端步骤；写明完成后的检查>

## 反意图审计
| 关键要求 | 字面合规但违背意图的实现 | 已补入的限制、反例或验收 |
|---|---|---|
| <要求ID> | <具体失败方式> | <对应防护> |

## 验收标准
- [ ] <可自动验证的二值检查及验证方式>
- [ ] <需要用户查看真实结果的人工检查，明确标为人工>

## 未决项与默认
<仍需人工确认的事项；其余默认及其撤销方式>

## 停止与澄清条件
<冲突、高风险、越权或意图不明时，暂停哪个分支并询问什么>
```

执行规格时遵守：

- 每条要求必须能追溯到根本目标或明确约束；无关修饰不进入实现。
- 遇到“字面合规但违背意图”的路径，不得利用规格漏洞；暂停相关分支并澄清。
- 新出现的低影响、可逆分支可采用默认并记录；高风险或不可逆分支不得自行决定。
- 完成后逐项报告“要求 → 实现 → 验证证据”。人工检查未执行时标为未验证，不得声称通过。
- 格式、测试或代理指标通过不等于目标达成；必须补充真实使用结果的目标层验收。

### 八、交付前做规格博弈与代理失效检查

在输出规格前，对每个 P0 或关键偏好至少构造一种“字面合规但真实意图失败”的实现，并把防护写回规格，而不是只列风险。

再检查两类假通过：

- **规格博弈**：满足文字、格式或测试，却偏离用户真正目的。
- **古德哈特式代理失效**：容易测量的指标达标，但用户可观察目标没有改善。

无法自动验证审美或体验时，明确保留人工验收；不得用“文档更完整”代替“结果更符合意图”。

## 输出契约

- 采访阶段只输出当前问题、具体选项、推荐答案和允许的简单回答；不展示理论名称、内部分析或价值评分。
- 结束采访时输出一份完整的执行规格代码块；若仍有人工确认项，再用一行列出，不提供多个风格版本。
- 用户要求立即实现时，当前 Agent 直接按最新规格执行并验收，不重新开始采访。
